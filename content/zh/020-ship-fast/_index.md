**贯穿案例 · 陈屿**

2026 年 3 月下旬，陈屿把第 1 章验证过的需求落了地：SnapPolish——给海外内容创作者和独立开发者用的截图美化工具，上传截图，加背景、边距、圆角、阴影和箭头标注，导出一张能直接发 X、Product Hunt 和博客的图。点子不新奇，但竞品差评区里明明白白写着用户的不满，关键词数据也对得上。这一次，他决定换个做法。

他先给自己立了规矩：13 天业余时间，做完就上线。上一个产品「坚持住」他做了整整 3 个月，功能越加越多，上线时热情已经耗掉大半，最后注册约 200 人、0 付费收场。这次他把想做的功能全部列出来，反复删，最后只留一条主线：上传 → 美化 → 导出。三步走通，产品就成立；三步之外的，全部进待办清单，等上线之后再说。

技术栈他没纠结，直接用独立开发者圈子里最常见的组合：Next.js 一个框架管页面和接口，部署放 Cloudflare，登录用 Clerk，收款接 Stripe，数据装 PostHog 和 GA4。他原本想买套现成模板省点事，看了一圈，要么技术栈对不上，要么塞了一堆用不上的功能。最后算了笔账：模板真正能帮他省的，主要是登录和支付的接线时间，而这两块恰好是 AI 写得最稳的"标准件"。于是决定：从零搭，但只搭需要的。

接下来 13 天，他白天上班，晚上和周末跟 Claude Code 结对干活。分工很明确：他拆任务、定接口、写验收标准，AI 负责写代码，他逐段审。核心的编辑器逻辑——画布拖拽、画箭头标注——AI 写得磕磕绊绊，他改了四五轮才顺；登录、Stripe 结账、落地页这些全世界都在写的代码，AI 几乎一次过。第 10 天他差点跑偏，想顺手加个"模板库"，页面画了一半停住，问自己：没有它，主线成立吗？成立。砍掉，排期保住了。

4 月 3 日晚，SnapPolish 上线。首月数据谈不上漂亮：访问 1,240、注册 96、付费 3 人，定价 9 美元/月，MRR 27 美元。但陈屿反而踏实：产品在第 13 天就见到了真实用户，之后每一步改进都有数据可依——这正是「坚持住」从头到尾都缺的东西。这一章，我们就拆开这 13 天：一个人，怎么把一个产品快速、完整地做出来。

## 2.1 先定 MVP：砍到只剩一条主线

很多人把 MVP 理解成"简陋版产品"，不对。MVP 不是简陋，是聚焦：把全部资源压在一条主线上，让用户能独立完成一次核心任务。别的功能再诱人，不在这条主线上，就先放下。

砍功能有一套可以重复使用的问法。先把所有想做的功能都写出来，不限数量，写满一页也没关系。然后逐条问三个问题：

1. 没有它，用户还能完成核心任务吗？能 → 砍。
2. 用户是冲着这个功能来的吗？不是 → 砍。
3. 上线之后再加，来得及吗？来得及 → 砍，进待办清单。

三个问题过完，剩下的通常不到原来的三分之一。SnapPolish 剩下的主线就是三步：上传截图、做美化、导出图片。模板库、历史记录、团队协作、批量导出，全被砍了。说明一句：批量导出后来成了用户呼声最高的功能，陈屿在 2026 年 9 月真的做了它——但那是上线五个月之后、数据指着鼻子要的时候。顺序不能反。

砍完功能，把上线日期钉死，再倒排每天做什么。**先定上线日期，再定功能清单；顺序一反，功能只会无限膨胀，产品永远上不了线。** 日期还有一个好处：取舍时不用纠结，只问一句"这个功能值不值得占掉我仅剩的两个晚上"，答案通常立刻清楚。

工期也要留缓冲。业余时间做产品，今天加班、明天有事，计划天然会被打断，所以排期按"实际能坐下来的晚上"算，不要按日历天数算。陈屿的 13 天里有 4 天完全没碰代码，他把编辑器核心这种硬骨头全排在周末，工作日晚上只做接线和页面这类轻活——这个排法本身，就是 MVP 思维的一部分：先保证主线不断，再谈进度。

最后是 MVP 的验收标准，它不是"功能都做完了"，而是这一句：**一个陌生用户，不靠你解释，能独立完成一次核心任务。** 做不到这一点，加再多功能也只是自我感动。

验收有个土办法：找一个没听过你产品的人，把链接发过去，只说一句"这是个给截图做美化的工具"，然后闭嘴，看他能不能自己走完三步。他卡在哪一步，哪一步就还没做到位；他问的每一个问题，都是你产品欠的一笔债。

## 2.2 标准装备：独立开发者的技术栈全景

一个人做产品，最大的浪费，是把时间花在"全世界都已经解决的问题"上：登录、支付、部署、统计……这些环节都有成熟服务在卖，价格低到个人开发者完全承受得起。你的时间，只该花在别人没有的东西上——你的产品本身。下面这张表，是出海独立开发者最常用的一套装备：

| 环节 | 选什么 | 干什么用 |
|---|---|---|
| 全栈框架 | Next.js / TanStack Start | 页面和接口在一个项目里写完 |
| 部署托管 | Cloudflare / Vercel | 部署上线、全球加速，不用自己管服务器 |
| 数据库 | 托管 Postgres（Supabase、Neon 等）/ Cloudflare D1 | 存用户、订单、订阅状态 |
| 登录 | Clerk | 注册、登录、找回密码、第三方登录 |
| 支付 | Stripe | 订阅收款、发票、退款、用户自助门户 |
| 行为分析 | PostHog | 看用户在产品里做了什么、哪一步流失 |
| 流量分析 | GA4 | 看用户从哪个渠道、哪个国家来 |
| 第三方 API | 官方 SDK 接入 | 模型、数据、邮件等外部能力 |

逐项说清。框架二选一：Next.js 生态最大、资料最多，是默认选项；TanStack Start 类型安全做得更彻底，喜欢它的路由和数据风格也可以选。别在二选一上耗超过一天，能开工的那个就是对的。部署也二选一：Vercel 是 Next.js 的"亲爹"，部署体验最顺，但流量涨起来后账单涨得快；Cloudflare 便宜、全球节点多，适合长期算账，出海产品用户在海外，托管更要放在海外。

数据库等真有东西要存了再上：用户、订单、订阅状态，这些是收费产品的命根子，用托管服务，别自己运维；纯工具站在早期甚至可以什么都不存。登录和支付则要从第一天就用现成服务：自己写登录，邮箱验证、密码安全、第三方登录个个是坑；自己处理支付，合规和状态同步能吃掉你一整周。分析工具两个都装，分工不同：**GA4 看人从哪来，PostHog 看人进来干了什么。** 装晚一天，早期数据就缺一天，而且永远补不回来。

最后是第三方 API 接入：AI 产品要接模型 API，工具产品常接数据 API。原则就三条：用官方 SDK；密钥只放在服务端的环境变量里，绝不写进前端代码；给每次调用加超时和失败处理——第三方服务抽风时，别把你的产品一起拖下水。

再说一句成本。这套装备在起步阶段几乎不花钱：部署、数据库、分析大多有免费额度，Clerk、PostHog 对小用户量也免费，真正按比例抽成的只有 Stripe（每笔交易抽成，这是行业惯例）。示意一下：产品跑到每月几千访问之前，你的固定支出大概率只有域名钱，一年十几美元。**出海做产品的门槛早就不在钱上，而在你肯不肯把这套装备认真接完。**

**判断一个环节要不要自己做，只问一句：用户会因为这一块比别人做得好而付钱吗？不会，就买现成的。**

## 2.3 买模板还是从零写：时间就是命

模板卖的不是代码，是一段已经接好线的半成品：登录有了、支付通了、落地页有了、部署脚本有了。你花钱买的，其实是"从空白仓库到能收钱"中间的那几天时间。

买之前先算账。自己从零接登录、支付和落地页，熟手要两三天，新手一周起步；一套模板大多一两百美元。你的业余时间如果按天算值这个数，买就划算；时间不值钱、又想练手，从零写也完全没问题。但模板有四个坑，付款前逐个看清：

- **技术栈对不上**：模板是 Vue，你要用 React。改栈花的时间比从零写还长，这种直接放弃。
- **长期没人维护**：看最后更新日期和作者回复 issue 的速度。停更的模板，等于花钱给自己埋雷。
- **塞了太多东西**：功能越全，结构越复杂。你花三天读懂它的代码，省下的时间又赔了回去。
- **只有皮没有骨**：有些"模板"只是好看的落地页，登录、支付全是占位图。买前把功能清单逐条对一遍。

付款前还有一个笨办法，但特别有效：把模板的演示站当成产品认真用十分钟。注册、登录、点购买（走到付款页就行），流程顺不顺、页面糙不糙，手感骗不了人。再把仓库（如果开放预览）或销售页的更新日志翻一遍，作者半年内有没有动过，一眼就知道。

还有一条中间路线：用框架官方脚手架、或口碑好的开源 starter 起步，免费，但接线自己来。有 AI 帮忙接线的今天，这条路的成本比过去低了很多——陈屿这次选的就是它：从零搭，但只用 AI 帮他接那些标准件。

结论不复杂：**模板的价值，按"能帮你提前几天上线"来算。能提前一周，值回票价；要花一周读懂它，分文不值。**

反过来也说一句：如果你正处在练手期，时间多、预算少，从零写一遍自有它的价值——登录和支付的整套接线经验，下个产品、下下个产品都还能复用。这笔账每个人情况不同，但一定要在动手之前算清楚，别开工三天了才想起来问。

## 2.4 AI 结对开发的正确姿势：拆任务、盯验收

先把角色摆正：Claude Code、Codex 这类工具是执行者，你是负责人。它写代码很快，但它不知道什么叫"对你的产品是对的"——这件事只有你能判断。所以 AI 结对开发的功夫，一大半花在动手之前和交付之后。

动手之前——拆任务：

0. 先给它交底：把项目的约定写成一份简短的说明文件放在仓库里——用什么技术栈、目录怎么分、命名什么规矩、哪些文件不许动。每次开工先让它读一遍。约定只写一次，后面每个任务都受益，省得你反复纠正同一个问题。
1. 把功能拆成小任务，每个小到"一句话说清输入和输出"。比如不要说"做导出功能"，要说"写一个接口：传入图片地址和导出参数，返回处理后的图片地址，出错返回错误码"。
2. 每个任务先配上验收标准：什么样算做完，用什么动作验。比如"未登录调用这个接口，应返回 401"。
3. 标准件放心交：登录、支付、增删改查这类全世界都在写的代码，它比你还熟。核心逻辑你亲自盯，必要时先自己写骨架，再让它往里填。

交付之后——盯验收：

0. 先让它复述一遍任务，你听它理解得对不对。理解错了就当场纠正，这一步花两分钟，能省下后面两小时的返工。
1. 逐段读代码，重点看异常路径：支付失败怎么办、接口超时怎么办、用户连点两下提交怎么办。AI 写顺畅路径很稳，坑大多埋在这些地方。
2. 按验收标准实测，不要听它汇报"已经实现了"。它说做完，你跑一遍，才算做完。
3. 看不懂的代码不要合并。今天看不懂，上线出故障时你更看不懂，最后背锅的还是你。
4. 每到一个能跑的版本，立刻提交 git。AI 写飞了的时候，一条命令退回上个版本，比逐行抢救快得多。

再避开三个常见误区：把需求写成一句许愿——"帮我做一个完整的 SaaS"——收到的是它一堆猜出来的代码；开一个超长的会话什么都往里塞，它记混需求，你也理不清账；只追求生成速度，一天写完三千行，接下来一周全在修。

**AI 普及之后，写代码的速度不再是瓶颈；能把需求拆清楚、把验收盯到底的人，才是真的快。**

## 2.5 把 SaaS 模块一个个接上：登录、支付、埋点

模块之间有依赖顺序，乱序接会返工。按这个顺序来：

第一步，登录（Clerk）。用户体系是地基：要收费，得先知道收谁的钱；要看数据，得先知道是谁的数据。接线内容就三样：注册/登录页面、第三方登录（Google 必须开，这是海外用户最主流的习惯，没有它注册转化会明显吃亏）、登录成功后的跳转。一切顺利的话，半天收工。

第二步，支付（Stripe）。一共四件事：① 在 Stripe 后台建好产品和价格；② 结账用 Stripe 托管的 Checkout 页面，不要自己写卡号表单，安全与合规都让 Stripe 担着；③ 接 Webhook——支付成功、续费失败、用户取消订阅，这些事件由 Stripe 通知你的服务器，你据此修改用户的订阅状态，这是整个支付的命门，本地调试时用 Stripe CLI 把事件转发到你的开发机上测；④ 打开客户门户，让用户自己换卡、取消订阅，省下你未来的客服时间。

第三步，埋点（PostHog + GA4）。只埋关键事件，不要贪多：注册完成、完成一次核心动作（对 SnapPolish 来说就是"导出图片"）、点击购买、支付成功。GA4 装上基础统计，看流量来源。埋点必须在上线前完成，上线之后再补，最早那几周的数据永远缺一块。

这三个模块的验收，各有一句现成的标准，照着测就行：登录，验"新用户从注册到进入产品不超过一分钟，中途不报错"；支付，验"测试卡付款成功后，数据库里这个用户的订阅状态立刻变成已付费"；埋点，验"你自己走一遍注册和导出，后台十分钟内能看到这两条事件"。三句话都通过，模块才算接完。听起来慢，实际上每个模块半天到一天足够，比上线后对着用户投诉排查便宜得多。

每个模块都守两条共同纪律：一、只用官方文档和官方 SDK，不抄来路不明的代码片段，出问题没人能帮你；二、密钥只进环境变量，绝不写进代码仓库，更不能提交到 GitHub。

**模块要一个一个接、一个一个验。三个模块一起上，真出了问题，你连是哪一家的锅都分不清。**

## 2.6 上线日：从本地跑通到用户能打开

本地跑通，只是万里长征第一步。你的电脑和生产环境之间，隔着一串最容易翻车的差异，先逐个排掉：

- **环境变量是两套**：本地的 .env 不会自己跟到线上，逐项核对生产环境的配置。Stripe 密钥记得从测试换成正式——漏换、错换，是新手上线第一大事故。
- **域名与 HTTPS**：绑定域名、等证书生效，裸域名和 www 两个地址都亲自打开试一遍。
- **生产数据库**：该建的表、该跑的迁移，在线上真正执行一遍，不要假设它和本地一模一样。
- **支付全链路自测**：用自己的真卡买一单最便宜的套餐，然后退款。测试卡测不出正式环境的配置错误，这一步省不得。

然后按这份上线检查清单逐项打勾，一项都别跳（这份清单建议存成文件，下个产品直接复用——它就是你的 SOP 资产，第 4 章会展开讲）：

- □ 生产环境打开首页、定价页、核心功能，逐页点一遍
- □ 用新邮箱注册一个账号，走完核心任务全程
- □ 真卡自购一单并退款，后台订阅状态正确变化
- □ GA4 实时报告里能看到自己的访问
- □ PostHog 收到注册、付费事件
- □ 隐私政策、服务条款页面已上线（收费产品必备，平台审核也会看）
- □ 404 页面、网站图标、分享用的 og 图齐全
- □ 出错能通知到你（邮件或即时消息），不要等用户上门来报
- □ 知道回滚按钮在哪：部署出问题，几分钟能退回上一个版本

时间上挑你之后几小时有空盯着的时段，别在深夜上线——真出问题，你需要清醒的几小时来处理。上线之后把链接发到你准备好的社区去（怎么找第一批用户，第 3 章细讲），然后盯着数据看板和邮箱过完第一天。

第一周也别急着加新功能。先看三件事：有没有人注册后卡在某一步（PostHog 的漏斗会告诉你）、有没有报错集中出现、付费链路有没有真实订单跑通。这一周的数据，决定你接下来一个月该修什么、加什么——这正是第 3、4 章要展开讲的。

**上线不是终点，是数据开始进账的起点。从这一天起，你做的每一个决定，都应该有数据垫底。**

## 本章要点

- MVP 只留一条主线：陌生用户不靠解释、能独立完成一次核心任务，就是合格的 MVP。
- 先定上线日期，再定功能清单；顺序反了，功能只会无限膨胀。
- 技术栈的第一原则是借力：登录、支付、分析都有现成服务，不要自己造。
- GA4 看用户从哪来，PostHog 看用户进来做了什么，两个都要在上线前装好。
- 模板买的是时间：能帮你提前一周上线就值，要花一周读懂它就不值。
- AI 是执行者，你是拆任务和验收的人；看不懂的代码不要合并。
- 模块一个一个接、一个一个验；上线前过检查清单，支付用真卡自购一单再退款，才算验完。

## 动手 Kata

**Kata 1：给你的产品写一页 MVP 定义。** 步骤：① 一句话写清核心任务（用户来做什么、做完得到什么）；② 不设限地列出全部想做的功能；③ 逐条过三问（没它主线成立吗、用户为它而来吗、以后加来得及吗），通过的留下，其余的移进待办清单。产出物：一份不超过 8 条的 MVP 功能清单，和一份待办清单。

**Kata 2：画一张你的技术栈决策表。** 步骤：① 对照 2.2 的全景表，逐项标注"第一天就需要 / 上线后再加 / 用不上"；② 每个"需要"的写一句理由；③ 把注册账号、实名认证、拿 API 密钥这些前置动作单独列出来，先办掉——它们最容易在上线日卡住你。产出物：一张填完的技术栈决策表。

**Kata 3：接通一个模块，并写验收标准。** 以登录或支付任选其一。步骤：① 先写 3 条以内的验收标准（例如"未登录访问付费页，跳转到定价页"）；② 按官方文档接线；③ 逐条实测，正常流程和失败流程各走一遍；④ 把踩到的坑记成笔记。产出物：一个验收通过的模块，加一页接线笔记。

**Kata 4：做一次完整的上线演习。** 步骤：① 把项目部署到 Cloudflare 或 Vercel 的线上环境，绑一个测试域名；② 按 2.6 的检查清单逐项打勾；③ 用 Stripe 测试卡走一遍付款，确认后台订阅状态正确。产出物：一份勾完的检查清单，和一个能发给朋友打开的链接。

## 翻车现场

有位开发者赶着 Product Hunt 的发布日，凌晨把产品部署上线，帖子发出去，点赞和评论都不错。第二天早上醒来，后台多了十几条注册，他很兴奋；但付费一单都没有。他以为是定价或转化出了问题，对着落地页改了一上午。直到下午有人私信问他"为什么付款页面写着测试模式"，他才反应过来：生产环境里的 Stripe 还挂着测试密钥——真实用户点下付款，看到的是一个假页面，钱根本收不进来。而真卡自购这一项，明明就写在他的上线清单上，他因为赶时间跳过了。

教训不复杂：上线事故大多不是代码写错了，而是"本地和生产的差异没人验"。检查清单不是形式主义，它就是前人用事故换来的。**凡是涉及钱的链路，上线前必须亲自用真金白银走一遍全程。**
