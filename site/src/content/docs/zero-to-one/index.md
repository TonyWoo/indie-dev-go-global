**贯穿案例 · 陈屿**

2026 年 10 月，SnapPolish 上线满半年。陈屿花了一个周末，把这半年攒下的数据整理成一个页面：累计访问 61,000、注册用户 4,120、付费用户 128 人、MRR 1,150 美元。离他"副业 MRR 到 2,000 美元就辞职全职做"的目标还差一截，但曲线是往上走的——这半年真正攒下来的东西，比数字本身更值钱。

他在页面上不光列数字，还写了一份复盘：需求最初是从哪找到的、上线首月只有 3 个付费用户时他想过什么、5 月为什么押注程序化 SEO、9 月为什么否决了呼声很高的录屏功能。每个月的拐点，他都对应到了当时做的那个动作上。

页面的最下面，他也没藏着掖着，贴上了 2025 年的「坚持住」：一个习惯打卡 App，业余做了 3 个月，注册约 200 人、付费 0 人，早已下线。条目旁边他写了一行小字：这是我交过的学费，也是我做 SnapPolish 之前唯一一段完整的独立经验。

为什么要费这个功夫？"做过独立产品"这五个字，口说无凭。无论你是想找合伙人、谈合作，还是有朝一日跳出去全职做这行，能拿出来证明自己的只有三样东西：**上线的产品、可查的数据、讲得清的故事。**

这一章就讲这三样东西怎么攒：为什么公司里的工作经验替代不了它们、作品集怎么做、数据怎么留痕、故事怎么讲、失败怎么摆上台面，以及那些数据工具到底该怎么用，才能真正指导你的决策。

## 6.1 公司经验替代不了独立经验

先把话说清楚：公司经验不是没用。陈屿 5 年大厂后端经验，让他能在 13 天业余时间里把 SnapPolish 的 MVP 做出来——架构怎么搭、支付回调怎么处理、线上出了问题怎么排查，这些手艺全是公司里练出来的。

但公司经验覆盖的，只是产品链条上的一段。在公司里，你写后端就只管接口，前端有专人做页面，增长有专门的团队，定价是产品经理和老板的事，用户投诉先落到客服那里，用户从哪来更是市场部的 KPI。每个岗位都是一颗螺丝钉，拧在自己那一段上，链条是别人替你接好的。

独立开发是把整条链一个人走完。不妨把两种模式摊开对照一下：

| 环节 | 在公司里 | 独立开发时 |
| --- | --- | --- |
| 找需求 | 产品经理负责 | 自己去社区和差评区挖 |
| 定价 | 老板和市场部拍板 | 自己定，定错了自己疼 |
| 获客 | 有品牌、有投放预算 | 从零找渠道，一分钱掰两半 |
| 收款与退款 | 财务和法务处理 | Stripe 接错了，钱就进不来 |
| 用户反馈 | 客服先过滤一层 | 骂声和表扬都直接砸向你 |
| 做不下去时 | 项目砍掉，换个组 | 全部沉没成本都是自己的 |

链条中间任何一环断了，产品就死给你看，没有同事可以商量，也没有背锅的人。更磨人的是决策方式的差别：公司里做决定有数据团队、有评审会、有上级兜底；独立开发时，信息永远不全，时间永远不够，你得在七成把握时就拍板，并且为全部结果负责。**这种"在不确定里做决定"的经验，公司里再资深也练不出来，因为公司本质上就是一套帮你分摊不确定的系统。**

还有个具体的例子。陈屿刚开始做 SnapPolish 时，下意识沿用了公司的习惯：先把后端架构想得漂漂亮亮，接口分层、扩展性都照顾到，光设计就花去好几个晚上。后来他回过神来——MVP 阶段用户根本不在乎你的架构，只在乎导出的图好不好看。公司里"把活做漂亮"是加分项，独立开发里"先活下来"才是及格线，这个优先级排序，他是交了几天时间成本才换过来的。

最后要说明，这不是劝你辞职裸奔。陈屿就是白天上班、晚上和周末做，副业状态照样攒独立经验。**公司经验给你的是深度，独立经验给你的是闭环，两者不互相替代。** 判断自己有没有独立经验，有个很简单的检验：脱离公司的品牌、流量和团队，你能不能把一个产品从零推到有人愿意付钱？如果答案是"没试过"，那你缺的不是技术，而是这一整段经历——而且这段经历必须留下痕迹，否则走完了也证明不了。这正是这一章接下来要讲的。

## 6.2 作品集：让你的产品自己说话

作品集的第一原则：**能打开的产品，胜过一百页 PPT。**

为什么？因为 PPT 里写什么都行，而一个在线的产品是没法造假的：链接点开，注册走一遍，功能用一次，真假立刻见分晓。你想证明自己，对方想核实你，双方的成本都最低。

具体怎么做？准备一个个人页面——自己的域名最好，没有的话用一个简单的聚合页也行——把你做过的所有产品列上去。每个产品只需要四样东西：一句话说清它解决什么问题、一个能点开的链接、当前状态（运营中 / 已下线）、上线时间。陈屿的个人站首页就是这么排的：SnapPolish 在最前面，卡片上放着实时更新的数据；下面紧跟着已经下线的「坚持住」。

注意，**下线的产品也要列，而且要标注下线原因。** 很多人只愿意展示成功的那部分，把失败的藏起来。但在懂行的人眼里，一个只有成功、没有失败痕迹的作品集反而可疑：要么你下场次数太少，要么你不敢复盘。把「坚持住」大大方方摆出来，写明"注册约 200 人、0 付费、已下线"，再附上复盘链接，这本身就是一种可信度。

作品集还应该收进你在公开渠道留下的痕迹：

- Product Hunt 的上线页面，Reddit 和 Hacker News 上的发布帖；
- 你在 X 上公开构建（build in public）时发的进度帖、数据帖；
- 用户给你的正面反馈原话、被周刊或媒体收录的记录；
- 每个产品背后的复盘文章链接。

这些链接拼在一起，就是一条任何人都能顺着点进去核实的时间线。找合伙人、谈合作、申请社区或孵化项目时，对方点完这条时间线，心里基本就有数了，根本不需要你自我吹嘘。

形式上别想复杂了：一页就够，按时间倒序排，最新的、最能打的放最前面。载体优先级是个人域名、其次是 GitHub 个人主页、再次是 Notion 这类公开页面——关键是地址稳定、打开快、不用登录就能看。排版花哨不加分，信息全、链接活着，才是硬通货。

作品集还有个隐形作用，是给未来的自己看的。人的记忆会漂移，半年后你可能连产品是哪天上线的都记不清，但作品集上写得明明白白。陈屿的习惯是每达成一个小里程碑就更新一次卡片——8 月 MRR 突破 500 美元那天，他顺手改了数字，前后不到一分钟。

最后给你一份作品集自查清单，每季度过一遍：

- 每个产品的链接还打得开吗？挂掉的及时修复或标注。
- 数据是最新的吗？超过三个月没更新的数字，要么更新，要么删掉。
- 状态标注诚实吗？实际上已经停更的产品，别还写着"运营中"。
- 新上线的、已下线的产品都补进去了吗？

作品集从来不是一次性作业，它是你在这行里的活简历，值得像维护产品一样维护它。

## 6.3 数据留痕：流量、用户、收入都要有据可查

人的记忆有个毛病：会自动美化过去。半年后你回忆产品的表现，"感觉增长不错"和"GSC 月点击从 210 涨到 3,860"，是完全不同的两个说服力等级。前者是印象，后者是证据。**而证据只能从第一天开始留，事后补不回来。**

这件事的关键在"基线"两个字。没有第一天的数字，就没有增长率；没有增长率，你的故事就只剩下孤零零的当前值，对方无从判断这产品是三个月做到的还是三年做到的、是在涨还是在跌。所以从产品上线第一天起，就把 GA4、PostHog、Google Search Console、Stripe 全部接好——这些工具的接入成本都是一次性的，晚接一天，数据就永久缺一天。

接好只是第一步，还要定期存档。后台数据会被各种因素干扰：改版埋点断过、统计口径调整过、免费版数据只保留一段时间。最稳妥的办法是每个月花十分钟，把关键页面截图存进一个固定文件夹，按"年-月"命名。陈屿存的就是这五类：

| 类别 | 留什么 | 从哪来 |
| --- | --- | --- |
| 流量 | 每月访问量、主要来源渠道 | GA4 / GSC 截图 |
| 搜索 | 展示、点击、核心词排名变化 | GSC 月度导出 |
| 用户 | 注册数、关键行为转化 | PostHog 里程碑截图 |
| 收入 | MRR 曲线、付费用户数 | Stripe 后台截图 |
| 决策 | 当时为什么这么定，一句话 | 自己的文档 |

第五类最容易被忽略，也最值钱：**每个关键决策，记一句话当时的理由。** 比如"7 月把价格从 9 美元涨到 12 美元，依据是最近两个月转化率稳定、且有用户说便宜得不像正经工具"。半年后复盘时，结论对不对反而是其次，能还原当时的判断依据，你才能分清哪次是运气、哪次是真本事——这直接决定你下一次还敢不敢下同样的注。

用户的原话也要留。在社交平台、私信、邮件里夸过你或骂过你的，截图存下来。讲故事的时候贴一句用户原话，比你自夸十句都管用；做决策的时候翻翻差评原话，也比看平均分清醒。

还有个细节：截图就截后台的原始界面，不要裁剪美化，更不要修图。在这个人人都会做图的年代，没修饰过的原始截图反而最有说服力——它传递的信号是"我的数字经得起你放大看"。日期水印、浏览器地址栏这类"不完美"的元素，留着比裁掉好。

陈屿在这件事上恰好有一正一反两个例子。SnapPolish 从第一天就接全了数据，所以半年后他能把每个拐点和动作一一对上号，复盘写得有根有据。而「坚持住」当年什么统计都没接，那"约 200 个注册"还是他后来去数据库里数出来的；用户在哪一步流失、为什么没人付费，完全无从查起——那个产品的复盘，一大半只能靠猜。

所以记住：**留痕的动作不难，难的是从第一天就开始，并且把它变成每月十分钟的固定习惯。** 等你需要证明自己的那一天再回头补，就像 6.2 说的，细节早忘光了，数据也长不回来了。

## 6.4 讲清你的故事：需求从哪来、哪些是你做的

有了产品，有了数据，还差最后一步：把它们组织成一个别人听得懂、信得过的故事。讲故事不是包装，更不是吹牛，而是把事实按照对方关心的顺序排好。

一个经得起追问的叙事结构是这样的：

1. **需求从哪来**：讲到源头，讲到具体。
2. **你做了什么判断**：那么多方向，为什么选这个。
3. **哪些是你做的**：你的角色和实际动手的部分。
4. **结果数字**：访问、注册、付费、收入，给全链条。
5. **下一步**：你接下来打算验证什么。

第一条最能区分真假。陈屿讲 SnapPolish 的需求来源，会说到："2026 年 3 月，我在 Reddit 和一个竞品的差评区泡了好几个晚上，发现内容创作者反复在抱怨同一件事——截图工具导出的尺寸和样式，不适合发 X 和 Product Hunt。"渠道、场景、用户的抱怨原话，全是具体的。对照一下，只会说"我敏锐地发现了一个市场机会"的人，一听就知道从没真正下场挖过——真挖过的人，嘴里全是地名和原话。

第三条要的是诚实，不是谦虚。一个人做的，就大方说全流程是我做的；用了现成模板、AI 帮你写了不少代码，也照实说。现在没有任何人会因为你用 AI 而扣分，但含糊其辞、一被追问就改口，会直接扣掉信任分。还有一种常见错误是把"我参与过"说成"我主导了"，在公司项目上尤其容易犯——对方只要问一句"这个决定是谁拍的"，就露馅了。

第四条记住：**数字给全链条，不要只挑最好看的那个。** 61,000 访问配上 128 个付费用户，单看转化率并不性感，但它真实，而且能让人一眼看出你的漏斗卡在哪一环，下一步该补哪里。只报访问、不谈付费，懂行的人立刻会追问收入，场面反而尴尬。

数字还要带上时间跨度。"注册四千多"和"上线半年、注册 4,120"，可信度完全不同：后者顺带交代了速度，听者自己就能算出月均增长。凡是孤零零、没有时间范围的数字，都默认会被打个问号。

同一个故事，面对不同的人，侧重要换：

- **对潜在合伙人**：多讲收入、成本结构和分工——他要判断这事能不能一起干。
- **对同行社区**：多讲增长方法和踩过的坑——干货换来的是人脉和口碑。
- **对招人的团队**：多讲你的判断和复盘——他们招的是能独立负责一摊事的人。

练习方法很简单：把你的主力产品按上面五段写成讲稿，朗读计时，压到五分钟以内。然后找一个同行听一遍，把他追问的问题全部记下来——**你答不上来的追问，就是你故事里的洞。** 回去把数据或复盘补上，洞就补好一个。下次再讲，故事就比这次硬一分。这个练习还有个附带好处：讲的次数多了，你会发现自己对产品的理解也在变深——很多当时没想通的决策，是在向别人复述时才真正想通的。

## 6.5 失败也要讲：没成的尝试和原因

在独立开发这一行，没有失败记录的人只有两种：刚入行还没来得及失败，或者在藏。真正下过场的人，人手几个下线的产品。所以失败不是污点，**不会复盘的失败才是。**

讲失败有个固定结构，照着填就行：做了什么 → 数据结果如何 → 死因分析 → 这笔学费换来了什么改变。

拿「坚持住」给陈屿上的课来说。做了什么：习惯打卡 App，业余开发 3 个月。数据结果：注册约 200 人，付费 0 人，已下线。死因他复盘出三条：

- **需求是自己想出来的，没验证过。** 他觉得现代人都需要一个"帮人坚持"的工具，但真实用户用备忘录和日历提醒就过得很好，这个痛根本不存在。
- **没有分发渠道。** 上线之后除了朋友圈，就没有任何地方能让新用户知道它存在，200 个注册里一大半是熟人捧场。
- **没设计付费点。** 从头到尾全免费，想着"先有用户再说"。可用户都没几个，付费更是无从谈起。0 付费不是运气不好，是设计出来的必然。

而这三条学费，直接变成了 SnapPolish 的三条纪律：先验证需求再动手写代码（第 1 章的方法）、上线第一天就想清楚用户从哪来、定价和 Stripe 收款第一天就接上。**一段失败经历的价值，就体现在它改变了你后来的哪个动作。** 改变不了任何动作的失败，才真的只是白交学费。

要讲的失败也不限于整个产品死掉。在跑的产品内部，砍掉的功能、跑输的实验、定错的价格，都是同一类材料。讲的时候同样用那套结构：当时为什么这么判断、数据怎么打脸、后来改成了什么。这种"小失败"甚至更常见、更真实，因为它说明你的产品还在动、你还在试。

讲失败还有两点分寸。第一，讲决策失误，不讲"我不够努力"。“当时太忙了，没坚持推广”这种话没有任何信息量，谁都能说；“我把没有分发渠道的产品先做了三个月，顺序反了”才是别人能借鉴、也能证明你真想明白了的复盘。第二，分清场合：对同行、对合伙人可以敞开讲，这是建立信任的方式；对正在用你产品的用户就没必要——他们关心的是产品好不好用，不是你的创业史。

最后说个反直觉的现象：把失败复盘认真写出来发出去，往往是你个人页面上最能引来同行的内容。陈屿那篇「坚持住」的复盘，时常有做独立开发的人顺着它来交流——大家手里都有下线的产品，只是很少有人把它讲清楚。

所以，顺序摆对了：**一个失败项目加一篇清醒的复盘，比三个半途而废、从不提起的项目值钱得多。**

换个角度想就更明白了：你去评估一个合作对象，他说自己从没失败过，你敢信吗？独立开发的成功率摆在那里，从没失败只说明样本太少。反过来，一个能把自己的失败讲得条条是道、每条都落到具体决策上的人，你反而会更愿意把事情交给他——因为他大概率不会在同一个坑里摔第二次。

## 6.6 用数据指导决策：工具不是摆设

最后聊聊工具。Ahrefs、Semrush、Similarweb、Google Search Console、OpenSEO——这些名字你多半见过，独立开发者的浏览器书签栏里总躺着几个。但工具装得多，不等于会用。**工具的价值不在打开它看数字，而在你能不能说出一句完整的话："因为我看到了 X，所以我决定做 Y。"**

先看两个免费的，它们其实是主力。GSC 是陈屿做程序化 SEO 的直接依据：2026 年 5 月，他在 GSC 里看到一批长尾词已经有了展示、排名卡在第二页附近，就是没人点——这说明 Google 已经认为他的站和这些需求相关，只差专门的页面去承接。于是他按场景批量做页面，到 7 月，GSC 月点击从 210 涨到了 3,860。细节第 3 章会展开，这里记住一点：**这个决定不是拍脑袋拍的，是数据指着方向，他跟着走而已。**

Ahrefs 和 Semrush 的用法是看竞品、找空位。把竞品的域名放进去，看它靠哪些词拿流量、哪些词竞争度低得反常，又有哪些用户需求它压根没做页面。打法随之清楚起来：竞品的主词别去硬碰，碰了也是给它当陪跑；打它没覆盖到的场景词和长尾词，用小成本一个个占住细分入口。提醒一句：具体某个词的搜索量是多是少，以你查询当下工具里显示的为准，不同工具口径还不一样，别把任何二手数字当圣旨背下来。

Similarweb 回答的是另一个层面的问题：这个赛道的流量到底从哪来。把几个竞品放进去看流量结构——如果访客主要来自自然搜索，说明这条道走得通，你可以跟进；如果主要靠付费投放撑着，你就得掂量钱包，跟进去烧钱大概率是送死。陈屿当年看完几个截图工具竞品的流量结构，确认了自然搜索是大头，才敢把宝押在 SEO 上、一分广告费不投。**这就是工具指导决策的样子：它帮你排除掉一条看起来很美的路。**

OpenSEO 这类开源工具适合做日常体检：定期跑一遍，查收录异常、死链、标题重复、加载速度，把报告里的问题清单当成任务单，一条条清掉。技术问题攒多了，会悄悄拖垮前面所有的内容努力，属于不声不响的那种失血。

把这一节和 6.3 接起来：每次用工具做了决定，就在台账里记一行"数据 → 决定 → 后来的结果"。攒上十几行，你就拥有了一份自己验证过的判断记录，下次拍板时腰杆会硬很多。比如陈屿台账里就有这样几行：

| 看到什么 | 决定什么 | 后来怎样 |
| --- | --- | --- |
| GSC 里一批长尾词有展示、没点击 | 按场景批量做程序化 SEO 页面 | 两个月后月点击 210 → 3,860 |
| 竞品流量以自然搜索为主 | 押注 SEO，不投广告 | 省下投放预算，流量稳步涨 |
| 定价实验期间转化率没有下滑 | 价格从 $9 涨到 $12 长期执行 | 8 月 MRR 突破 $500 |

最后，避开两个极端。一种是数据洁癖：没数据绝不动手，什么都要先验证三个月——机会不等人，数据永远"还不够"，等你觉得够了，窗口已经关了。另一种是数据装饰：决定早拍好了，再翻几个数字给自己背书，被人一追问就穿帮。**工具是参谋，拍板的永远是你；但拍过板之后，记得回头看一眼结果，把账记上。**

## 本章要点

- 公司经验给你深度，独立经验给你闭环，两者不互相替代。
- 作品集的核心是能打开的产品加可查的数据，下线的产品也要列明原因。
- 数据留痕必须从第一天开始：流量、注册、收入、反馈、决策理由，缺了补不回来。
- 故事按"需求来源 → 你的判断 → 你做的部分 → 结果数字 → 下一步"讲，具体到渠道和用户原话。
- 失败要讲决策失误和它改变了你后来的哪个动作，不讲空泛的"不够努力"。
- 工具的价值在于"因为看到 X，所以决定做 Y"，而不是装了多少个。

## 动手 Kata

**Kata 1：做一张你的产品清单页**
步骤：找一个能公开访问的页面（个人域名、Notion 公开页或 GitHub 个人主页均可）；列出你做过的全部产品，含已下线的；每个产品写一句话介绍、状态、链接、上线时间。
产出物：一个可公开访问的作品集页面。

**Kata 2：给在跑的产品补上数据留痕**
步骤：按 6.3 的五类清单逐项检查，缺的分析工具（GA4、PostHog、GSC、Stripe）当天接上；把当前的关键数字截图存进一个固定文件夹，并设一个每月重复的日历提醒。
产出物：一个数据存档文件夹，内含第一次完整存档。

**Kata 3：写一篇失败复盘**
步骤：选一个没成的尝试，按"做了什么 → 数据结果 → 死因 → 换来的改变"四段写，控制在 800 字以内；发到你的作品集页面或公开账号上。
产出物：一篇已公开发布的复盘短文。

**Kata 4：五分钟讲故事演练**
步骤：按 6.4 的五段结构，把你的主力产品写成讲稿；朗读计时，反复删改到五分钟以内；找一位同行听一遍，记下他所有的追问。
产出物：一份讲稿，加一份"追问与待补材料"清单。

**Kata 5：建一张决策台账**
步骤：回忆最近三个月的产品决定，逐条补记"依据什么数据 → 做了什么决定 → 结果如何"；今后每做一个关键决定，当天就记一行。
产出物：一份决策台账文档（表格形式即可）。

## 翻车现场

有位开发者，产品数据其实不差，月访问有几万、也有真实付费。一次和人谈合作，对方想确认他的运营能力，请他当场打开 Google Search Console 和 Stripe 后台对一眼数。他支支吾吾半天，最后承认：GSC 从来没接过，Stripe 的图也拿不出来，平时报的数字都是他从服务器日志和零散订单里"估"出来的。数字本身八九不离十，但合作当场就黄了。

问题不在数字真假，在于他整段经历拿不出任何可核查的证据。在对方眼里，一个连自己核心数据都随手估的人，谈到收入分成和长期投入时，是没法让人放心的。

教训就一句：**你的经历有多可信，不取决于数字有多大，取决于任何人想核查时，你能不能立刻把后台打开。** 留痕这件事，等需要证明自己的那天再补，是补不回来的。
